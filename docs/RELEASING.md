# Версии и релизы SongKit

## Правила

- Источник версии — `package.json`; тот же номер в корне `package-lock.json` и `packages[""].version`. Футер собирается из него.
- Семантическая версия `X.Y.Z`: MINOR — новые совместимые функции, PATCH — исправления и изменения интерфейса опубликованного релиза, MAJOR — несовместимые изменения. Пока проект 0.x, несовместимые изменения отдельно описывать в changelog и плане миграции.
- До слияния и полной проверки использовать `X.Y.Z-rc.N`. Несколько исправлений в одном неопубликованном кандидате можно объединить; уже опубликованный RC неизменяем, следующее изменение получает rc.N+1.
- Тег — аннотированный `v` + точная версия пакета. Не перемещать и не перезаписывать опубликованные теги.
- GitHub Release связан с тегом и содержит явные изменения, проверки, ограничения и ссылки. RC помечается prerelease и не назначается Latest. Стабильный релиз — только коммит main после зелёного CI; Pages дополнительно требует успешного deploy.
- Pattern v2 и Draft v1 не являются номерами приложения. При смене формата нужны отдельная миграция, тесты и описание отката.

## Подготовка

1. Обновить package/lockfile, раздел CHANGELOG и актуальные документы. Не оставлять противоречащие текущему UI инструкции; исторические отчёты явно обозначить.
2. Собрать с `BASE_PATH=/songkit/`, выполнить `npm run docs:screenshots`, просмотреть мобильные и desktop PNG. Manifest содержит номер версии и размеры; не менять только его номер без обновления снимков.
3. Выполнить `npm run check`, `npm run test:e2e`, `npm run format:check`. После коммита/отправки дождаться CI именно этого SHA.
4. Обновить PR: итоговый объём, результаты тестов, незавершённая ручная приёмка. Стабильная публикация требует разрешённого слияния в main; создание prerelease не подменяет его.

## Тег и GitHub Release

После подтверждения правильного SHA и зелёного CI (пример для кандидата):

```powershell
git tag -a v0.4.0-rc.1 <verified-sha> -m "SongKit 0.4.0-rc.1"
git push origin v0.4.0-rc.1
gh release create v0.4.0-rc.1 --verify-tag --prerelease --latest=false --title "SongKit 0.4.0-rc.1" --notes-file release-notes.md
```

Для каждого релиза обязателен отдельный раздел CHANGELOG с категориями «Добавлено», «Изменено», «Исправлено», «Удалено» по необходимости, проверками и ограничениями. Ссылки внизу changelog ведут на сравнение тегов. Заметки GitHub Release формируются из того же раздела, чтобы не расходились:

```powershell
npm run release:notes -- 0.4.0-rc.1 .tools/release-notes.md
```

Передать файл через --notes-file. Для стабильного релиза убрать prerelease, выбрать SHA из main с успешным verify и подтвердить Pages по deployment/HTTPS. Если тег уже существует, сверить его SHA; несовпадение — ошибка, а не повод force-push. При ошибке в опубликованном коде выпустить следующий PATCH или RC.

GitHub Releases не публикуют npm-пакет (`private: true`) и не меняют GitHub Pages: CD реагирует только на push в main. Никакого автоматического merge в процессе тегирования нет.

Команды и связь releases/tags сверены с [GitHub CLI](https://cli.github.com/manual/gh_release_create) и [GitHub Docs](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).
